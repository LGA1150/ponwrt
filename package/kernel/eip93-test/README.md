# Direct EIP93 Crypto API tests

`kmod-eip93-test` supplies `eip93_test.ko`, a correctness test module for Linux
6.18. Tests run during `insmod`; results go to the kernel log. The module has
no device binding, changes no EIP93 registers and is never loaded automatically.
It works with either the stock or out-of-tree EIP93 module. Load that driver
first; this package deliberately does not select one of the competing drivers.

Release 10 supplies `eip93_ctr_bench.ko` for a separate
[aligned CTR length and queue-depth throughput sweep](README.ctr-bench.md).
The correctness matrix and its replay case numbers are unchanged.

The separate [standalone hardware test](../eip93-hw-test/README.md) measures
NULL-copy and AES-CTR without the EIP93 crypto driver. It binds the hardware
directly and must be run with the normal driver unloaded.

For the remaining kTLS throughput difference, driver release 37 adds
[aggregate profiling and a capture runner](../eip93/README.profile.md).
These measurements are separate from this correctness module.

The test chooses each **EIP93 driver name explicitly**, avoiding generic-name
selection of a software implementation. It compares against explicitly named
software implementations and includes 44 known-answer vectors selected from
Linux `crypto/testmgr.h`. It does not depend on `CONFIG_CRYPTO_SELFTESTS` or on
the boot-time crypto self-tests being enabled. Driver release 27 disables
PonWrt's size-based AES fallback by default, so valid nonempty small AES
requests also exercise hardware. Stock drivers and earlier package releases
may use software *inside* the selected EIP93 driver through 512 bytes for
AES-128 or 256 bytes for AES-192/256.

Matrix plaintext, hash input and AAD are pseudorandom bytes generated by
**synchronous software AES-CTR**, explicitly selecting `ctr(aes-generic)`
through `crypto_alloc_sync_skcipher()`. Valid ciphertext for decryption is
then generated independently by the algorithm's synchronous software reference.
Known-answer vectors retain their published inputs and outputs.

## Build and run

Select `kmod-eip93-test` under Cryptographic API modules. With a matching prepared
PonWrt kernel, build just this package:

```sh
make package/kernel/eip93-test/compile V=s
```

After installing the package and loading the EIP93 driver:

```sh
insmod eip93_test
dmesg | tail -80
rmmod eip93_test
```

Successful insertion leaves a module with read-only `tests`, `failures`,
`skipped` and `async_ops` counters in `/sys/module/eip93_test/parameters/`.
`tests` counts case repetitions and tag-size checks, not individual crypto requests.
The module drains requests before returning an error on a test failure.
Unavailable hardware algorithms are logged individually as `SKIP`; a partial
run ends with `PASS-PARTIAL`. No matching tests, or no available selected
algorithm, fails insertion rather than reporting success.

To test the hash changes first, or narrow down a failure:

```sh
insmod eip93_test group=hash stop_on_failure=1
rmmod eip93_test
insmod eip93_test 'alg=hmac(sha256)' verbose=1
rmmod eip93_test
insmod eip93_test 'alg=authenc(hmac(sha256),cbc(aes))' stop_on_failure=1
```

Each failed case reports its algorithm, case number, known-answer flag (`kat`),
message/key/AAD/tag lengths, layout, IV pattern, streaming mode and seed. A
matrix case (`kat=0`) can be replayed independently. Substitute the reported
seed and case number:

```sh
insmod eip93_test 'alg=hmac(sha256)' case_id=123 seed=1 verbose=1
```

Case numbers are stable when `max_size` changes; `case_id` excludes known-answer
vectors and the tag-size sweep. For a known-answer failure, rerun that algorithm
with `verbose=1 stop_on_failure=1` and no `case_id`. Use `max_size=1025` for a
shorter matrix; known-answer vectors still run. Change `seed` to vary the
matrix data and keys. By default (`seed=0`), each module load chooses a fresh
random seed, prints it in the startup log and exposes the actual value in
`/sys/module/eip93_test/parameters/seed`. An explicit nonzero seed makes runs
repeatable. The payload generator uses a fixed public test key and separate
counter streams for each seed, algorithm, case and input purpose. Replaying
one case therefore generates the same bytes as running the entire matrix,
independently of algorithm filters, `max_size` or synchronous/async targets.
Keys and IV patterns remain derived from the same recorded seed. This is a
test-data generator, not a source of secret keys. Unload a successful run before
starting another. Failed insertion leaves no loaded test module.

Release 4 adds `repeats=1..10000` (default 1). Each repetition allocates fresh
request buffers and uses identical generated inputs, keys and IVs. Failure
and verbose-start messages include `repeat=N/total`. With
`stop_on_failure=0`, repetitions continue after crypto/data failures so the
summary reports their frequency; allocation failures or timed-out operations
still stop the algorithm. Tag-size validation is not repeated.

`lengths=...` accepts up to 32 comma-separated payload lengths, each at most
`max_size` (65,536 by default). It requires `case_id` and substitutes only that
case's message length, retaining its key, IV, AAD, tag, layout and stream
parameters. The seed and case ID retain the same generated data prefix.
Default case numbering and the original matrix are unchanged. For example:

```sh
insmod eip93_test 'alg=authenc(hmac(sha224),rfc3686(ctr(aes)))' \
    case_id=323 seed=1708171853 lengths=16368 repeats=100 stop_on_failure=0
```

Driver releases 17 through 19 can handle this case entirely in software.
Release 20 restores its hardware path by default after lowering the DMA
thresholds; no partial-word override is needed.

Test release 8 adds `aad_length=0..1024` for an explicit AEAD `alg` and
`case_id`. The default `-1` retains the case's AAD length. The override
preserves case numbering, key, IV, tag size, layout and seeded input prefix;
it changes the split between AAD and plaintext in that generated stream.
It applies to both the software reference and target before buffers are
allocated. The upper bound includes EIP93's native word-offset limit of
1020 and the next aligned fallback size, 1024. Unsupported native AAD
lengths still use the driver's existing software fallback. The focused
AAD 0/4/8 replays below use native authenc for nonempty payloads.

## Normal-use policy

Driver release 36 uses raw `dma_maxburst=6`, 64/64 buffer thresholds and
`aes_sw_fallback=0` (no size-based AES software fallback).
Eligible read-only AES skcipher sources can be byte-aligned. DES/3DES and
all native authenc sources bounce unless word-aligned. Release 26/27's
short-input-only authenc guard also allowed a long request to fail.
Authenc computation still uses hardware after the source copy. Existing
software authenc fallbacks, SG/block constraints, destination/in-place
cache-line isolation and private authenc decryption output remain enforced.
Release 31's `skcipher_partial_src` switch is for diagnosis and remains off
for normal use; it removes the partial-block source copy for eligible CTR
requests only while enabled. Release 32 adds the separate default-off
`skcipher_tail_align` experiment described below. Release 33 lets that
experiment overread the original source SG without requiring `pad_src=1`;
release 34 extends it to eligible multi-entry CTR sources, including GCM/CCM
requests. Release 35 handles partial blocks between source entries with
software keystream bytes while keeping full spans in hardware. The flag
remains off for normal use. Release 36 overlaps CTR output at logical offsets
and uses one bounced-output copy, as described in the
[contiguous-output replay](#contiguous-ctr-output).

Rebuild and install `kmod-eip93`, then reload the driver with its defaults
after releasing existing users. Test module release 6 can verify the CTR fix;
release 7 adds CBC failure diagnostics and release 8 adds AAD replay control. Verify
`dma_maxburst` reads `6`; an explicit load-time override takes precedence.
`aes_sw_fallback` should read `N`. If it reads `Y`, reload the driver without
that override or with `aes_sw_fallback=0`; it is read-only after load because
fallback allocation and request sizing depend on it.
Clear any previous diagnostic settings before the full correctness run:

```sh
cat /sys/module/crypto_hw_eip93/parameters/dma_maxburst
cat /sys/module/crypto_hw_eip93/parameters/aes_sw_fallback
(
  eip93_params=/sys/module/crypto_hw_eip93/parameters
  for parameter in skcipher_unaligned_src skcipher_partial_src skcipher_tail_align \
      aead_unaligned_src \
      skcipher_dma_debug aead_dma_debug aead_debug \
      aead_src_offset aead_dst_offset; do
    echo 0 > "$eip93_params/$parameter" || exit 1
  done
  insmod eip93_test.ko seed=1708171853 repeats=3 \
    stop_on_failure=1 && rmmod eip93_test
)
```

No bypass is needed to exercise eligible unaligned AES sources in this run.
The unaligned-source experiments below deliberately bypass the retained
guards; keep those switches off for normal use.

For a focused AES hardware run, reuse the same test module and select the
three algorithms affected by distribution patch 926:

```sh
for cipher in 'ecb(aes)' 'cbc(aes)' 'ctr(aes)'; do
  insmod eip93_test.ko "alg=$cipher" seed=1708171853 repeats=3 \
    stop_on_failure=1 || break
  rmmod eip93_test || break
done
```

Each matrix covers all three AES key lengths and includes small requests.
Zero-length requests are no-ops and malformed ECB/CBC lengths are rejected.
`aes_sw_fallback=1` at driver load restores the old thresholds for a comparison;
it does not change the independent authenc fallbacks.

## CTR completion regression

With size-based fallback off, the device matrix reports 198 ordinary CTR
IV mismatches across three repetitions. Ciphertext checks pass. All those
messages consume a final counter whose low word is `ffffffff`: the engine
wraps its low 32 bits without carrying into the high 96 bits of the returned
IV. Release 29 fixes this completion carry, retaining the existing split
when wrap occurs inside a message. Reuse test release 6 to validate it:

```sh
insmod eip93_test.ko 'alg=ctr(aes)' seed=1708171853 repeats=3 \
  stop_on_failure=1 && rmmod eip93_test
```

The matrix checks both directions, partial final blocks, all three key
lengths, internal wraps and exact-end wraps. A full run has 3,564 cases.

## CBC input-threshold comparison

AES-CBC case 234 also exposes an intermittent final-block corruption with
a 512-byte input at source offset 1. The focused device replay failed on
repetition 596 of 1,000, while offset 4 passed all 1,000 repetitions. This
is separate from CTR IV completion. Release 29 keeps eligible unaligned
AES-CBC sources directly mapped; it adds no CBC source bounce or fallback.

To test DMA refill timing, keep raw `dma_maxburst=6` and the output threshold
at 64. With the engine idle between runs, change only the input threshold
in `PE_BUF_THRESH` (AN7581 address `0x1fb7010c`):

| Register value | Input threshold | Output threshold |
| --- | --- | --- |
| `0x00400040` | 64, baseline | 64 |
| `0x00400020` | 32 | 64 |
| `0x00400080` | 128 | 64 |

The input field is bits 7:0 and specifies free buffer bytes needed before
an input transfer starts. The output field is bits 23:16 and specifies
available output bytes. Replaying each setting with the same parameters
isolates the effect of the input field:

```sh
insmod eip93_test.ko 'alg=cbc(aes)' case_id=234 seed=1708171853 \
  src_offset=1 repeats=10000 stop_on_failure=1 && rmmod eip93_test
```

The driver restores 64/64 thresholds when reloaded. A passing threshold
experiment still needs repeated DES/authenc comparisons before it can
replace their source-alignment workarounds.

Test release 7 also prints the first bad CBC block, its chaining value and
the input recovered by applying the opposite software operation to that
block. It uses the initial IV for block zero and the preceding ciphertext
for subsequent blocks. This supports both directions, AES/DES/3DES and
in-place or separate output buffers. `different` is a byte-position mask
within that block; `0x8000` means only byte 15 of an AES block differs.
Rebuild `kmod-eip93-test` to get these diagnostics; existing replay options
and generated test data are unchanged.

For the case-234 hypothesis, replacing input byte 511 with byte 507 in the
software model produces the same reported mismatch range and first bad
byte (`5b` to `72`). The new `CBC inverse` line lets a device run compare
the entire recovered input. A structured substitution would support a
fault in the device's input path. Inversion alone cannot distinguish a
DMA read error from internal input alignment or cipher-state corruption.
The modeled substitution predicts `different=0x8000`, with the recovered
input's final byte `46` instead of `38` (the value at input byte 507).

## Long authenc input regression

On release 26, SHA224/RFC3686 case 740 intermittently corrupts the final
three payload bytes and the four-byte tag with a source offset of one.
The request processes 65 AAD bytes plus 16,385 payload bytes. Its destination
already bounces, but the source is direct under the release 26/27 policy.
In the reported comparison, offset 1 passed 100 repetitions and then failed
on repetition 28 of a second run. Offset 4 passed both 100-repetition runs.

Release 28 bounces all unaligned native authenc sources. After loading the
new driver with the defaults above, reuse test release 6 for a focused replay:

```sh
insmod eip93_test.ko 'alg=authenc(hmac(sha224),rfc3686(ctr(aes)))' \
  case_id=740 seed=1708171853 repeats=1000 stop_on_failure=1 &&
  rmmod eip93_test
```

Then rerun the full matrix with three repetitions. Keep `aead_unaligned_src=0`;
enabling it bypasses the workaround. `aead_dma_debug=1` can confirm a source
copy in a short replay, but keep logging off during the longer run because
it changes timing. This addresses source alignment; it does not establish
the physical cause of corruption.

## Investigating intermittent corruption

Release 3 reports the first and last differing byte offsets, separate counts
for payload and tag bytes, and the expected/actual byte at the first mismatch.
Offsets are measured from the start of the scatterlist, including AAD.
For case 281, payload bytes occupy offsets 13 through 1037 and the tag occupies
1038 through 1069. For example, `data_bytes=0 tag_bytes=32` means the ciphertext
matched but every byte of the generated tag differed. The first-byte sample
comes from the test module's generated test data. Guard and SG metadata errors
retain their existing error reports.

With `kmod-eip93` release 15, optional driver diagnostics distinguish a raw
hardware error from a software tag comparison failure. After installing both
updated modules and loading the driver, replay the intermittent SHA-256/CTR
case until it fails or reaches 100 trials:

```sh
echo 1 > /sys/module/crypto_hw_eip93/parameters/aead_debug
for trial in $(seq 1 100); do
    insmod eip93_test 'alg=authenc(hmac(sha256),rfc3686(ctr(aes)))' \
        case_id=281 seed=1708171853 stop_on_failure=1 || break
    rmmod eip93_test || break
done
echo 0 > /sys/module/crypto_hw_eip93/parameters/aead_debug
dmesg | tail -80
```

`authenc hardware error` prints the raw descriptor status and length words.
`authenc tag mismatch` prints request dimensions and a `different` mask, where
bit 0 corresponds to tag byte 0. These messages are also expected for the
intentional corrupted-tag/ciphertext/AAD checks during a passing trial. An
unexpected valid-decrypt failure is identified by `target decrypt returned
-74, expected 0` and `FAIL`; include the preceding driver message in a report.
The diagnostics retain the existing checks and do not retry or mask failures.
The accompanying `authenc verification error` line includes raw result status
and length; `hw_err=0 err=-74` means hardware reported success and the driver's
tag comparison failed.

Release 30 adds `input_tag` and `output_tag` to that mismatch line, each
limited to the configured tag size. They use the same byte order as the
software comparison, including the SHA word conversion. DMA diagnostics
also print `thresholds`, read from `PE_BUF_THRESH`, alongside `dma_cfg`.
Both diagnostics remain off by default.

## SHA1/CBC case 267

With the source bypass enabled, this case fails its first valid decrypt
at source offset 1, while offset 4 passes 20 repetitions. Both controls
use direct source DMA for decryption and private destination buffers.
The comparison reproduces at raw `MXBRSTSZ=6` after an earlier log showed
raw 15. Hardware reports success, but the driver finds all 12 tag bytes
different. The 60 authentication errors in the passing control are the
three deliberately corrupted-input checks in each repetition.

Encryption still copies its 1,028-byte source because AAD plus plaintext
is not divisible by the AES block size. Decryption includes the 12-byte
tag in its source mapping, making 1,040 bytes, so the existing length check
permits a direct read from the unaligned source. The engine processes the
first 1,028 bytes; the input tag is compared by the CPU. Thus encryption
success does not establish that unaligned source DMA works in this case.

The software model predicts these tags for seed `1708171853`:

| Input consumed by the engine | Tag |
| --- | --- |
| Correct AAD and ciphertext | `9c5e41454bb18494c430058e` |
| Byte 1027 changed from `d8` to `f5`, reusing byte 1023 | `b42de3a74f62d9354f5e95c6` |

The release-30 device replay now matches both tags exactly, with
`dma_cfg=0x180006 thresholds=0x400000`, `src_copy=0` and `hw_err=0`.
Repeating with raw burst 5 (`dma_cfg=0x180005`) and the same thresholds
fails the first valid decrypt with exactly the same two tags. Thus raw 5
does not avoid this input substitution, despite passing earlier DES tests.
This strongly confirms the earlier DES four-byte-back substitution in the
HMAC input, rather than merely a mismatching tag. The exact location of
the fault within the DMA input path or word-alignment logic remains unknown.

In that replay, the source starts at `0x82983081`. Byte 1027 is at
`0x82983484`, but its value matches byte 1023 at `0x82983480`. The engine
processes 1,028 bytes, while the DMA mapping covers 1,040 bytes through
`0x82983490`, including the original authentication tag. The final input
word is therefore fully mapped; its transfer is shortened by the command's
processing length. It is not at a 1 KiB or 4 KiB address boundary.

The documented descriptor does not have separate DMA-fetch and crypto
lengths. Its bypass field counts whole words, so it cannot skip a one-byte
prefix after rounding this source address down. Extending the packet length
would change the HMAC message. The SHARC reference also specifies that
HMAC always finalizes each operation, so splitting the request into two
ordinary authenc descriptors is not a transparent workaround.

Rebuild only `kmod-eip93` for release 30; test release 7 can be reused.
With other crypto users idle, pin raw burst 6 and input/output thresholds
0/64, then collect a short unaligned replay. Reloading the driver restores
64/64 thresholds, so apply the experimental value after loading it:

```sh
(
  p=/sys/module/crypto_hw_eip93/parameters
  trap 'echo 0 > "$p/aead_unaligned_src"; echo 0 > "$p/aead_debug"; echo 0 > "$p/aead_dma_debug"; devmem 0x1fb7010c 32 0x00400040' EXIT
  devmem 0x1fb70120 32 0x00180006
  devmem 0x1fb7010c 32 0x00400000
  echo 0 > "$p/aead_src_offset"
  echo 0 > "$p/aead_dst_offset"
  echo 1 > "$p/aead_unaligned_src"
  echo 1 > "$p/aead_debug"
  echo 1 > "$p/aead_dma_debug"
  insmod eip93_test.ko 'alg=authenc(hmac(sha1),cbc(aes))' \
    case_id=267 seed=1708171853 src_offset=1 repeats=20 \
    stop_on_failure=1 && rmmod eip93_test
)
```

Expect `dma_cfg=0x180006 thresholds=0x400000`. Report the `input_tag` and
`output_tag` immediately before an unexpected valid-decrypt failure. This
experiment adds no source-alignment workaround and retains authenticated
copyback: a mismatching tag still returns `-EBADMSG` without releasing the
private decrypted output.

### Input-end alignment sweep

Keep the source one byte past word alignment and vary the physical ending
alignment of the processed input. CBC requires block-multiple payloads;
the RFC3686 CTR authenc variant permits byte steps while retaining AES and
HMAC-SHA1. Case 267 still selects four AAD bytes, a 63-byte HMAC key and a
12-byte tag. With the diagnostic source bypass enabled, these flat,
out-of-place CTR requests use direct source DMA in both directions.

| Payload bytes | Processed bytes including AAD | End-exclusive address modulo 4 |
| --- | --- | --- |
| 1023 | 1027 | 0 |
| 1024 | 1028 | 1 |
| 1025 | 1029 | 2 |
| 1026 | 1030 | 3 |
| 1027 | 1031 | 0 |

Use the existing release-30 driver and release-7 test module; no rebuild
is needed. With other crypto users idle, select raw burst 6 and thresholds
0/64 explicitly, since the previous burst-5 comparison or its cleanup may
have left different values. Disable per-operation driver logging and keep
testing after a mismatch to cover all five lengths:

```sh
(
  set -e
  p=/sys/module/crypto_hw_eip93/parameters
  trap 'echo 0 > "$p/aead_unaligned_src"; devmem 0x1fb70120 32 0x00180006; devmem 0x1fb7010c 32 0x00400040' EXIT
  devmem 0x1fb70120 32 0x00180006
  devmem 0x1fb7010c 32 0x00400000
  devmem 0x1fb70120 32
  devmem 0x1fb7010c 32
  echo 0 > "$p/aead_src_offset"
  echo 0 > "$p/aead_dst_offset"
  echo 0 > "$p/aead_debug"
  echo 0 > "$p/aead_dma_debug"
  echo 1 > "$p/aead_unaligned_src"
  insmod eip93_test.ko 'alg=authenc(hmac(sha1),rfc3686(ctr(aes)))' \
    case_id=267 seed=1708171853 src_offset=1 \
    lengths=1023,1024,1025,1026,1027 repeats=20 stop_on_failure=0 &&
    rmmod eip93_test
)
```

The two register readbacks should be `0x00180006` and `0x00400000`.
The cleanup disables the source bypass and restores the driver's normal
raw-6 and 64/64 settings.

The device replay reports exactly this input-ending pattern:

| Payload bytes | Passed trials | Failed trials | Wrong payload bytes | Wrong tag bytes |
| --- | --- | --- | --- | --- |
| 1023 | 20 | 0 | 0 | 0 |
| 1024 | 0 | 20 | 1 | 12 |
| 1025 | 0 | 20 | 2 | 12 |
| 1026 | 0 | 20 | 3 | 12 |
| 1027 | 20 | 0 | 0 | 0 |

Every failure is an encryption mismatch, starting at SG byte 1027 and
ending at 1039, 1040 or 1041 respectively. The failing trials stop before
valid decryption. The summary's 260 asynchronous operations account for
40 complete passing trials (five operations each) plus 60 failed encrypts.
The pasted test log contains no driver register snapshots; the requested
settings were raw burst 6 and thresholds 0/64 as above.

Regenerating this case's plaintext in software gives bytes `d6 f0 2d` at
SG offsets 1023..1025 and `38 99 76` at 1027..1029. Replacing the final
one, two or three bytes with their values four positions earlier predicts
every reported mismatch range and byte count, including the first
ciphertext byte changing from `4d` to `a3`. Equivalently, CTR inversion
gives `38 XOR 4d XOR a3 = d6` at offset 1027. The full erroneous ciphertext
and tags were not printed, so those remaining byte values are predictions.

Both word-ending lengths pass despite their unaligned source start.
This strongly supports corruption while reading or realigning the final
partial input word. It does not identify the exact failing hardware stage
or establish a general fix for every cipher and alignment.

### Source-offset control for the input-end sweep

The same five lengths were replayed at source offsets 2, 3 and aligned
offset 4. The table gives passing trials out of 20, including offset 1
from the earlier sweep. Every failing trial stops at encryption:

| Source offset | 1023 bytes | 1024 bytes | 1025 bytes | 1026 bytes | 1027 bytes |
| --- | --- | --- | --- | --- | --- |
| 1 | 20 | 0 | 0 | 0 | 20 |
| 2 | 0 | 0 | 0 | 20 | 20 |
| 3 | 0 | 0 | 20 | 20 | 20 |
| 4 | 20 | 20 | 20 | 20 | 20 |

The word-ending controls pass, but so do three additional partial-word
endings: offset 2/length 1027 and offset 3/lengths 1026 and 1027. Therefore
an unaligned source plus a partial final word is not sufficient to predict
failure. The aligned source passes all 100 trials. The driver probe confirms
raw burst 6; this paste does not include the buffer-threshold readback.

The first bad SG byte moves from 1027 at source offset 1 to 1026 at offset
2 and 1025 at offset 3. The test's page allocation places data at
`128 + src_offset`, so all these failing payload bytes occupy the word at
allocation offset `0x484`. The extra partial-word passes end in the next
word, `0x488`. These are allocation-relative positions; the latest log has
no DMA address snapshots. They do not establish a particular bus width or
burst boundary, since request length and source position both changed.

For offset 2 the first effective plaintext byte changes from `fe` to `cd`,
the value four bytes earlier; for offset 3 it changes from `2d` to `70`.
The same substitution predicts all five reported failure signatures,
including the eleven changed tag bytes at offset 2/length 1024. However,
the simple model that corrupts every unaligned partial-word tail would
also fail the three extra passing controls. Its trigger condition is
incomplete, even though the input-byte substitution matches the failures.

### Fixed-length source-address control

Keep payload length 1024, AAD length 4, the seed and IV unchanged, and move
the source by whole words: offsets 1, 5, 9 and 13. All sources remain
one byte past word alignment, and all processed inputs end one byte into
their final word. Those final words are at allocation offsets `0x484`,
`0x488`, `0x48c` and `0x490` respectively. This separates source-position
effects from changing the crypto request length and contents.

The device replay fails all 20 encrypts at each offset: 80 failures with
the identical signature `first=1027 last=1039 data_bytes=1 tag_bytes=12
expected=4d actual=a3`. The bad payload byte moves with the source through
all four final words. It is therefore not tied to allocation offset
`0x484`, and shifting the source by these whole-word distances does not
avoid it. The extra passing partial-word cases in the earlier sweep also
changed request length, so length-dependent behavior remains a candidate.
The probe confirms raw burst 6; the pasted kernel log again omits the
buffer-threshold readback.

### Four-byte length steps

An eight-byte pattern counted from the source's containing word initially
fit the 23 source-offset/length combinations, including the extra passes:

```text
m = source address modulo 4
phase = (AAD bytes + payload bytes + m) modulo 8
candidate failure condition: m != 0 and phase is 5, 6 or 7
```

The broader device replay below rejects this candidate. It must not be
used as a DMA eligibility check or as evidence of a 64-bit bus.

The replay held source offset 1 and AAD length 4 fixed and stepped the
payload length by four bytes on both sides of 1024. Every processed input
still ended one byte into its final word:

| Payload bytes | Candidate prediction | Observed result per length |
| --- | --- | --- |
| 1024 | Fail | 20/20 fail |
| 1016, 1032, 1040 | Fail | 20/20 pass |
| 1020, 1028, 1036, 1044 | Pass | 20/20 pass |

Only length 1024 fails, with the same `first=1027 last=1039 data_bytes=1
tag_bytes=12 expected=4d actual=a3` signature. The other 140 trials pass
encryption, valid decryption and the three corrupted-input rejection
checks, accounting for 720 asynchronous operations overall. At all eight
lengths the generated final input byte differs from the byte four positions
earlier, so the passing cases cannot hide that substitution through equal
data values. The fault remains localized near 1024 in this tested window;
no longer period or internal buffer boundary has yet been established.

### Broader length comparison

Keep case 267, source offset 1, AAD length 4 and the same seed. Compare
payload lengths four bytes below, at and above 64, 128, 192, 256, 512, 768,
1024 and 2048. These include SHA1's 64-byte hash-block size, larger sizes
and non-power-of-two multiples. All 24 requests still end one byte into
a partial input word, and all source SG pieces fit in one allocated page.
For this seed, every selected final byte differs from its four-byte-back
counterpart.

The device replay confirms `dma_cfg=0x00180006 thresholds=0x00400000`
and reports:

| Center payload bytes | Center minus 4 | Center | Center plus 4 |
| --- | --- | --- | --- |
| 64 | 20/20 pass | 20/20 pass | 20/20 pass |

affect the original CTR output prefix.

extra input locally even across a counter-wrap split; it must not follow
`sg_next()` past the supplied entry. This remains a default-off diagnostic
for AES CTR/RFC3686 CTR covered by one source entry with distinct source

### Testing the CTR overread through kTLS

Release 34 adds the multi-entry path needed for this test. See the
[multi-entry replay](#multi-entry-ctr-tail-alignment) below for current
instructions. The following routing limitation describes release 33.

Release 33's overread path is not reached by nonempty kTLS AES-GCM
records using Linux's generic GCM implementation. In `crypto/gcm.c`,
`crypto_gcm_init_common()` prepends a 16-byte tag-mask block to the payload
SG, and `crypto_gcm_init_crypt()` submits `payload_length + 16` bytes to
CTR. The request therefore has at least two source entries, even if the

tag block before submitting its CTR request.

source entry, but it does not enable the tail-overread path. GCM setkey also
uses a single-entry in-place CTR request; that is outside the diagnostic's
scope. Smaller records, TLS 1.2 versus 1.3, and recv/send/splice do not remove
the GCM/CCM prefix entry.

### Contiguous CTR output

Driver release 36 (patch 043) removes the gaps between output chunks in
the opt-in `skcipher_tail_align=1` path. Every descriptor writes at its
logical output offset. The next descriptor overwrites extra output from
the preceding descriptor's source overread. Software boundary spans are
filled after all hardware DMA has finished and before any result is copied
to the caller, preserving distinct SG tables that alias the same pages.
Completion uses one `sg_copy_from_buffer()` call for the original length.

This relies on ordered packet output. The ADSP-SC58x/ADSP-2158x SHARC+
Processor Hardware Reference, revision 1.0 (September 2017), describes
packet output writes finishing before the result descriptor on page 44-27,
and advancing to the next command after writing the result descriptor on
page 44-36. The local model implements that ordering. The subsequent Airoha
trace and repeated tests below also exercise overlapping output DMA.

Source SG entries and their mappings are unchanged. Each hardware read
still extends by `-(source_dma + logical_length) & 3`, with no `256n` length
filter. Independent counter states prevent those extra bytes from advancing
the next chunk's logical counter. The output allocation covers the furthest
write end, including a hardware chunk followed only by a short software
tail. At most three extra bytes lie beyond the logical result, plus normal
cache-line rounding; there is no intermediate slot padding or compaction.

The DMA summary adds `output`, the required output extent before cache-line
rounding. `process + sw_bytes - tail = text` still holds. For the existing
page-crossing case below, the model reports `text=4097 process=4106 tail=9
sw_bytes=0 output=4100`, with six hardware descriptors. The descriptor at
logical offset 1024 writes 1027 bytes; the next starts at output offset
2048 and overwrites the three extra bytes. The final partial chunk and
the low-word counter wrap are covered in the same request.

### CTR across partial SG entries

This section records release 35. Release 36 changes its output layout and
copyback as described in the [contiguous-output section](#contiguous-ctr-output).

Driver release 35 (patch 042) extends `skcipher_tail_align=1` to nonempty
CTR source entries of arbitrary length, with distinct source/destination
SG tables. The source is mapped unchanged. A non-block-multiple intermediate
entry no longer makes the driver copy the entire source into a bounce buffer.
The same-table in-place path and other cipher modes retain their existing
handling.

Hardware processes spans starting at logical AES block boundaries, including
the final partial block when it starts at such a boundary. Software handles
the bytes of blocks split across source entries. For example, a 20-byte
first entry uses hardware for its first 16 bytes; its last four bytes and
the next entry's first twelve bytes use one software-generated keystream
block. The following hardware span resumes at the next logical counter.
Adjacent software spans are combined, so many one-byte entries do not need
one plan entry or AES operation per source entry. DMA-coalesced source
segments can use hardware across their original SG boundaries.

The expanded CTR key is retained per transform. Software reads the original
SG only after source/output/state DMA mappings have been released, then
finishes every boundary span in private output before copying any result
back. This ordering supports distinct SG tables that alias the same pages.
No source DMA bounce or private source SG is introduced. Requests composed
entirely of split blocks complete through the existing submission worker
without publishing a hardware descriptor. This handling is independent of
the size-based `aes_sw_fallback` switch; that switch remains disabled by
default. `skcipher_tail_align` also remains disabled by default.

The DMA trace adds `sw_bytes`. `process` counts hardware input bytes,
`tail` counts discarded hardware overread bytes and `descriptors` counts
hardware descriptors. Thus `process + sw_bytes - tail = text`. An entirely
software boundary request has `process=0`, `descriptors=0` and
`sw_bytes=text`, and still has `src_copy=0`.

### Multi-entry CTR tail alignment

This section records release 34. Release 35 removes its intermediate-entry
length restriction as described in the [partial-entry section](#ctr-across-partial-sg-entries).

Driver release 34 (patch 041) extends `skcipher_tail_align=1` to AES CTR
requests with multiple source entries and distinct source/destination SG
tables. Every intermediate source entry must end on a logical AES block
boundary; the final entry may have any length. Generic GCM/CCM's 16-byte
prefix plus payload can now use the experiment. Same-table in-place
requests and layouts with partial blocks between entries retain their
existing handling.

The driver maps the supplied source SG unchanged. Each planned descriptor
overreads up to three bytes to end its input on a word boundary, including
at intermediate entries. No source copy or private source SG is added.
Plans use the mapped segment count and addresses, so DMA-coalesced entries
are supported. Each extension stays in the final source word and cannot
newly cross a 1 KiB or page boundary.

Every descriptor has an independent counter computed from its **logical**
position. Its state is mapped read-only and hardware IV saving is disabled.
Extra bytes cannot advance the next descriptor's logical counter. Splitting
at low-counter wrap uses logical lengths; a wrap affecting only discarded
output needs no split. Descriptor lengths also stay within the 20-bit field.
Separate padded output slots prevent one descriptor's extra writes from
overlapping another's output. Completion copies only logical bytes back,
and ordinary CTR returns the IV advanced by the original request length.
All allocations and mappings finish before submission, with cleanup on
preparation failure and no added wait between descriptors.

TLS 1.2 recv retains its direct-to-user asynchronous path. EIP93's private
output adds its own copy before delivery, so TLS 1.3 recv can incur an
additional payload copy as well as batch allocation and wait overhead.
These code differences are candidates for the performance gap, not a
measured attribution. TLS 1.2 splice uses the same kernel-buffer batch
path as TLS 1.3.

After the suggested RX splice comparison (`-j 2 -p 0 -w 0 -r 5`), the
reported medians are:

| TLS version | RX mode | Reported median throughput (Gbps) |
| --- | --- | ---: |
| 1.2 | splice | 0.752420 |
| 1.3 | splice | 0.718228 |

The input threshold was not restated in this report. Within this splice
comparison, TLS 1.3 is 4.54% slower than TLS 1.2, a smaller version gap
than the earlier recv results. TLS 1.3 splice is approximately 1.66% faster
than its reported recv median. This supports investigating the differing
recv paths as a substantial contributor to the earlier gap. Splice also
changes pipe work, syscall counts and benchmark prefill, so these medians
do not isolate copying from allocation, batching or scheduling costs.
Batch occupancy and submission gaps remain useful profiling targets.
The passing tail-alignment replay does not establish the hardware mechanism
behind the TLS 1.2 threshold effect.

### CTR source-tail alignment experiment

Driver release 32 adds `skcipher_tail_align=1` to test the suggested
workaround: process up to three extra bytes so that the **source end
address**, not the length alone, is word-aligned. At source offset 1,
logical lengths 4/5/6 process 7 bytes, and 260/261/262 process 263 bytes.
CTR's output prefix is unchanged by processing more input bytes.

This applies to AES CTR and RFC3686 CTR with distinct source/destination
SG tables and one source entry covering the request. It uses only extra
space already declared in that source SG entry; it neither copies the
source nor extends the mapping. The experiment returns `-EMSGSIZE` if the
entry lacks the required space or the extended descriptor exceeds its
20-bit length field. `pad_src=1` provides enough space for the grids below.
Padding rounds to 128 bytes, so a length already at that multiple does
not gain space; for example, length 256 at source offset 1 is rejected.

When extra bytes are processed, the driver allocates private destination
space and copies back only the original length. The caller's destination
padding remains untouched. Ordinary CTR returns the IV advanced by the
original number of AES blocks, even when the extension consumes another
block. Counter-wrap descriptor splitting uses the processed length.
ECB/CBC, native authenc, same-table in-place buffers and multi-entry
sources retain their existing paths. The opt-in flag remains off normally.
Both device replays below pass, including normal thresholds, all AES key
sizes and ordinary CTR counter wrap. The path still requires source padding
and one source entry with distinct source/destination tables.

The extension remains inside the final aligned word, so it cannot newly
cross an aligned 1 KiB or page boundary. The source SG extent is checked
as well: sharing an IOMMU page alone does not establish that the extra
bytes are part of the supplied DMA buffer. Test release 8 can be reused;
rebuild and reload only the release-32 driver. Keep other crypto users idle
while changing the shared DMA settings.

The first two requests log `text=4 process=7 tail=3` and
`text=260 process=263 tail=3`, with `src_copy=0 dst_copy=1`. The grid then
runs without per-request logging. The raw burst and threshold settings
match the failing controls; cleanup restores the normal defaults.

## DMA boundary and burst experiments

Use `kmod-eip93` release 20 and test release 4 for these controls. The driver
sets both input and output buffer thresholds to 64 (`PE_BUF_THRESH=0x00400040`)
for all devices. Cases 281 and 323 now use hardware by default, and the engine
appends the computed tag to the packet. The former `aead_allow_partial`
parameter has been removed. Keep unrelated crypto users stopped during the test.

The driver parameters `aead_src_offset` and `aead_dst_offset` shift its bounce
buffers independently. This changes the actual DMA address, whereas changing
the test's SG offset alone does not move a page-aligned driver bounce buffer.
Offsets are byte counts, smaller than `PAGE_SIZE`, and must be both word- and
cache-line-aligned. Zero retains normal placement; nonzero forces that side
to bounce. The examples use 128-byte multiples, suitable for the target's
64/128-byte cache-line alignment.

First choose the burst setting when loading the driver, after unloading the
test and releasing any other references to the driver:

```sh
rmmod crypto_hw_eip93
insmod crypto-hw-eip93 dma_maxburst=6
```

`dma_maxburst` is a read-only, load-time **raw field encoding** (`0..15`), not
a byte count. It defaults to `6` from driver release 25; an explicit `-1`
preserves the value found at probe. The driver
changes only register `0x120` bits `[3:0]` and prints the before/after readback.
For the reported configuration, `6` and `5` should read as `0x00180006` and
`0x00180005`. The SHARC+ manual describes this field's interaction with bursts,
1 KiB boundaries and short transfers, but does not establish its encoding
conversion or the exact Airoha interconnect behavior.

After loading release 20, verify the buffer threshold register on AN7581:

```sh
devmem 0x1fb7010c 32   # expected: 0x00400040
```

The input/output threshold register is independent of the maximum burst
field. Record both values when comparing experiments. Replaying a larger
output threshold also restores exposure to the previously observed fault;
there is no partial-word software guard in release 20.

Run the following in a subshell to restore the prior diagnostic parameters
afterward. It captures one verbose DMA sample for each geometry, then repeats
with driver logging disabled because logging can affect an intermittent fault.
Each passing insertion is unloaded; failed insertion leaves no test module.

```sh
(
    set -e
    p=/sys/module/crypto_hw_eip93/parameters
    old_src=$(cat "$p/aead_src_offset")
    old_dst=$(cat "$p/aead_dst_offset")
    old_log=$(cat "$p/aead_dma_debug")
    trap 'echo "$old_src" > "$p/aead_src_offset";
          echo "$old_dst" > "$p/aead_dst_offset";
          echo "$old_log" > "$p/aead_dma_debug"' EXIT
    run_case() {
        if insmod eip93_test \
            'alg=authenc(hmac(sha224),rfc3686(ctr(aes)))' \

            rmmod eip93_test

    }
    for offsets in 0:0 128:0 0:128 128:128; do

        run_case verbose=1 lengths=959,960,961,962,963,964,965,4031,4032,4033,4034,4035,4036,4037,16368
```

Adding case 323's 63-byte AAD makes the two small sweeps process 1022..1028
and 4094..4100 bytes. They include word-multiple controls and all tail byte

its AAD is 13 bytes. In release 20, packet DMA output includes the tag again:

Then reload with `dma_maxburst=5` and repeat the same matrix. Explicitly reload

## Unaligned skcipher source experiments

Use driver release 23 or later and test release 5 or later. Driver release 26
keeps the four-byte source check for DES/3DES; eligible AES sources no longer
need a bypass. Root-only parameters under
`/sys/module/crypto_hw_eip93/parameters/` support the experiment:

- `skcipher_unaligned_src=1` bypasses the source offset check only for
  skcipher requests with distinct source and destination SG tables. Block
  lengths, destination cache-line isolation, in-place requests and authenc
  retain their checks. Unaligned source DMA has failed device tests; this
  switch affects qualifying skcipher requests while enabled.
- `skcipher_partial_src=1` (driver release 31) bypasses the final source
  block-length check for AES CTR skcipher requests contained in one SG
  entry, with distinct source and destination tables. It leaves source
  start-offset policy, destination checks, in-place requests, multi-entry
  source SG checks and other cipher modes unchanged. See the
  [plain-cipher/authenc comparison](#plain-cipher-versus-authenc).
- `skcipher_tail_align=1` tests source-end alignment for CTR requests with
  private output. Release 32 requires mapped source padding; release 33
  overreads the supplied source SG directly without extending its mapping
  or requiring caller padding. Release 34 also supports multiple source
  entries whose intermediate lengths are AES block multiples. Release 35
  handles blocks split across entries with software boundary processing.
  Release 36 overlaps output at logical offsets and copies the result once.
  See the [contiguous-output replay](#contiguous-ctr-output),
  [partial-entry replay](#ctr-across-partial-sg-entries),
  [unpadded-source replay](#ctr-overread-with-unpadded-sources) and
  [multi-entry kTLS replay](#multi-entry-ctr-tail-alignment).
- `skcipher_dma_debug=1` logs the mapped addresses and lengths, bounce use,
  raw DMA configuration, thresholds, each submitted descriptor and final
  completion. The driver logs no keys or packet bytes.

Test release 5 adds `src_offset` and `dst_offset` (0..127, default `-1` retains
the case layout), plus `pad_dst=1`. They require an explicit `alg` and
`case_id` selecting a flat, out-of-place skcipher case. Release 6 also accepts
AEAD cases and adds `pad_src=1`. In-place and fragmented layouts, and hashes,
are rejected for these overrides. Offsets are added to the existing 128-byte
allocation offset; `src_offset=1` therefore starts at allocation offset 129. These
controls preserve the case ID, key/IV placement, key, IV and seeded payload.
The software oracle retains its ordinary aligned layout.

`pad_dst=1` rounds the destination SG extent to 128 bytes while preserving
the requested crypt length. With `dst_offset=0`, the destination owns whole
64/128-byte cache lines even for a 16,368-byte message. Padding is poisoned
and checked after the operation, including bytes beyond the usual guard.
Source SG lengths remain unpadded unless `pad_src=1` is requested. Confirm
actual DMA placement from the driver logs: an unaligned test address alone
does not prove unaligned DMA.

Keep both thresholds at 64 and `MXBRSTSZ` at the same raw value throughout
the comparison. For the original AN7581 baseline, the diagnostic mapping
line should show `dma_cfg=0x180006 thresholds=0x400040`. If another burst
setting is loaded, use the load-time `dma_maxburst=6` control described above.

First replay case 322 with the default source bounce behavior:

## AEAD source padding and offsets

Test release 6 extends the existing source/destination offset overrides
and `pad_dst` control to flat, out-of-place AEAD cases, and adds `pad_src` for
both skciphers and AEAD. These controls work with driver release 24 or later.
Release 28 guards all unaligned authenc sources; this experiment bypasses it.

`pad_src=1` rounds the source SG extent up to a multiple of 128 bytes without
changing the input bytes, key, IV, AAD, tag or requested crypt length. On
AEAD decryption the logical source includes the received tag. Source padding
is filled with the guard pattern and checked after completion, including
bytes beyond the ordinary 32-byte guard. The software reference keeps its
aligned, unpadded layout. These controls require an explicit algorithm and
case ID with a flat, out-of-place layout; hashes and in-place/fragmented
replays are rejected. Padding does not align the source start address.

At raw `MXBRSTSZ=6`, the case-14 payload-length sweep failed at one byte;
lengths 2 through 8 each passed 20 repetitions. AAD stayed five bytes and
the source offset stayed one. Payload lengths 1 and 5 have the same source
end alignment, so a partial final word alone does not explain the observed
failure. The six-byte input spans two partial words without a complete
aligned word between them. The passing longer inputs include a complete
word. That distinction is a hypothesis, not a hardware guarantee.

The subsequent offset sweep failed at offsets 1 and 5 with both six-byte
and 128-byte source mappings. Offsets 0, 2, 3, 4, 6 and 7 passed with either
mapping size, with one repetition per combination. Source padding alone
therefore does not fix case 14. Both failing offsets place the six input
bytes across two partial words without a complete aligned word between them.
Release 26 conservatively bounces unaligned authenc sources below eight
processed bytes. Release 28 extends this to all lengths after the case-740
regression; the experimental bypass can still reproduce the fault.

The comparison below keeps the six-byte encryption input fixed and varies

## Coverage

All 32 algorithms registered by Linux 6.18 EIP93 are listed in `algorithms.h`:

- AES ECB/CBC/CTR and RFC3686 CTR, with 128-, 192- and 256-bit AES keys;
  DES and 3DES ECB/CBC.
- MD5, SHA-1, SHA-224 and SHA-256, both plain and HMAC.
- Authenc combining each of those four HMACs with AES-CBC, RFC3686 AES-CTR,
  DES-CBC and 3DES-CBC.

The matrix combines every supported cipher key length (or every HMAC key
length), every message size and every layout. IVs, streaming styles, AAD sizes,
authenc HMAC key sizes and tag sizes rotate through those combinations; this
is a deterministic covering matrix with freshly seeded payloads, not the full
Cartesian product.

- **35 message sizes**, from zero to 65,536 bytes: cipher/hash block and hash
  padding boundaries, 255/256/257 and 511/512/513 fallback boundaries,
  4 KiB page boundaries, 16 KiB TLS sizes and long requests. Invalid ECB/CBC
  lengths must be rejected. Authenc decryption may reject malformed input
  with `EINVAL` or `EBADMSG`, depending on which check runs first.
- **11 layouts**: separate buffers, in-place buffers, different SG tables
  aliasing the same pages, even/uneven SG splits, different source/destination
  splits, page-crossing entries, and chained SG tables of 64-byte entries.
  Buffer offsets include 0, 1, 3, 4, 7, 15, 63 and 127. Keys and IVs are also
  placed at different offsets. Source data, SG metadata and surrounding
  poison bytes are checked after each operation. Hash result buffers are
  guarded and tested at different offsets too.
  Driver release 28 permits eligible byte-aligned read-only AES skcipher
  sources. DES/3DES and all native authenc inputs retain source alignment
  safeguards; destinations and in-place buffers also require
  cache-line isolation. Use `aead_dma_debug=1` for a selected authenc case
  or `skcipher_dma_debug=1` for a skcipher to confirm submitted addresses
  and bounce use.
- **IVs**: zero, seeded data, low 32-bit CTR counter at `0xfffffffe`, and all
  ones. Ordinary CTR messages spanning several blocks cross the counter
  boundaries. RFC3686 supplies its own internal counter. CBC/ordinary CTR
  output IVs are compared against software; AEAD/RFC3686 IV mutation is not
  assumed to be part of their API contract.
- **Hash operations**: one-shot `digest`, `init/update/final`,
  `init/update/finup`, and export/import into a fresh request before continuing.
  Updates include zero bytes, partial blocks and chunks crossing a 64-byte
  boundary. Export/import covers buffered-only and already-processed state.
  Long one-shot hashes can require more descriptors than one hardware ring.
  HMAC key lengths are 0, 1, 16, 63, 64, 65, 131 and 256 bytes.
- **Authenc**: aligned and non-word-aligned AAD lengths from 0 to 65, truncated
  tags in four-byte steps up to the full digest, and both orders of `setkey`
  and `setauthsize`. Long HMAC keys are combined with truncated tags to test
  key normalization. A separate sweep checks that hardware rejects zero,
  oversized and non-word tag lengths without changing the accepted authsize.
  Tag, ciphertext and AAD corruption must each fail authentication; plaintext
  is not required to remain untouched after an authentication failure.

Encryption is checked against software ciphertext, and decryption receives
the software ciphertext independently. A round trip alone cannot hide a bug
shared by the driver's encrypt and decrypt paths. Known answers additionally
check the software references used as oracles. Native GCM/CCM are not EIP93
algorithms; the kTLS benchmark covers their generic compositions separately.

Requests use the Crypto API completion/backlog contract, with `MAY_SLEEP`
alternating between cases. Each operation is awaited, so this tests correctness
and large-request ring rollover, not concurrent-request queue saturation or
throughput. A completion warning is printed after `timeout_ms` (default 10000).
There is no generic Crypto API cancellation: a stalled request keeps its
buffers and module code alive until the real completion arrives. In that
situation `insmod` remains blocked; it must not free memory still owned by DMA.

## Host validation

The source can also be compiled as an ordinary external module:

```sh
make -C /path/to/prepared/linux-build M="$PWD/src" W=1 modules
```

For a software-only harness check, use a kernel with the corresponding generic
ciphers, modes, authenc, hashes and HMAC implementations enabled. Then run:

```sh
insmod eip93_test.ko software=1 seed=1 stop_on_failure=1
rmmod eip93_test
insmod eip93_test.ko software=1 software_async=1 seed=1 stop_on_failure=1
rmmod eip93_test
```

`software_async=1` also requires `CONFIG_CRYPTO_CRYPTD` in the test kernel.
It wraps the software targets in `cryptd` while keeping
the references synchronous. Both modes are labelled **SOFTWARE HARNESS
VALIDATION (no EIP93 tested)**. They validate the test harness and its async
lifetime handling, not the hardware driver or noncoherent DMA behavior.
